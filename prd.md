Project: Personal Embedded Development Tracker 1. Objective Build a clean, lightweight personal web application called Embedded Dev Tracker for me as an embedded systems engineer. I want to use this website whenever I start a new embedded project. It should help me organize my development lifecycle, track daily engineering tasks, maintain phase-wise checklists, record technical notes, and verify that my product is ready before I give a demo or move to pilot deployment. This is a personal productivity tool for one engineer, NOT a company-wide platform. Do not build enterprise features, complex role management, manufacturing management, company dashboards, or unnecessary integrations. Prioritize simplicity, usability, persistence, and a professional engineering workflow. 2. Technology Stack Use: ● Next.js with App Router. ● TypeScript. ● Tailwind CSS. ● shadcn/ui for UI components. ● Lucide icons. ● SQLite for simple persistent local storage, using Prisma ORM. ● Local file storage for optional attachments. Keep the architecture simple and easy to maintain. The application should run locally on my computer. Document how to install, start, back up, and restore it. Do not require paid services, external databases, or cloud accounts for the basic functionality. 3. Main Navigation Create a left sidebar containing: 1. Dashboard 2. My Projects 3. Development Lifecycle 4. Product Release Gates 5. Engineering Notes 6. Settings Use a clean, professional dark/light theme suitable for daily engineering work. 4. Dashboard Create a personal dashboard that shows: ● Total projects. ● Active projects. ● Completed projects. ● Tasks due today. ● Overdue tasks. ● Pending tasks. ● Blocked tasks. ● Projects currently in each development phase. ● Release gates with incomplete checklists. ● Recently updated projects. ● Quick action to create a new project. Display project progress based on completed tasks, but show release readiness separately. A project must not be considered ready for a demo or pilot merely because its development tasks are complete. 5. Project Management Allow me to create, edit, archive, and delete my personal projects. Each project should contain: ● Project name. ● Project description. ● Project ID. ● Project category. ● Hardware platform. ● MCU/SoC. ● Development environment and IDE. ● Programming language. ● RTOS or Embedded Linux details, if applicable. ● Repository URL, optionally. ● Start date. ● Target completion date. ● Current development phase. ● Project status. ● Project-specific technical notes. Examples of projects I may manage: ● STM32 firmware development. ● Silicon Labs FreeRTOS applications. ● ESP32 Matter devices. ● Embedded Linux applications. ● Sensor drivers and communication protocols. ● Robotics and edge-AI projects. These are examples only. Allow any project name and hardware platform. When I create a project, initialize its development phases from a reusable default lifecycle template. Each project must have its own tasks, checklist progress, notes, and release-gate results. 6. Development Lifecycle Create a phase-based lifecycle for every project. Use these default phases: Phase 1: Requirements and Planning Checklist examples: ● Define project objective. ● Define functional requirements. ● Define hardware and software requirements. ● Select MCU/SoC and development board. ● Identify peripherals and interfaces. ● Define acceptance criteria. ● Create project repository. ● Record project risks and assumptions. Phase 2: Hardware Study and Bring-up Checklist examples: ● Review datasheet and reference manual. ● Verify board power supply. ● Verify clock and reset configuration. ● Verify GPIO configuration. ● Verify debugger connection. ● Verify UART logging. ● Verify required peripheral interfaces. ● Record hardware issues and observations. Phase 3: Firmware Architecture and Development Checklist examples: ● Define firmware architecture. ● Create modular project structure. ● Configure the build system. ● Implement drivers. ● Implement middleware and application logic. ● Handle errors and timeouts. ● Add logging and diagnostics. ● Review memory usage. ● Review interrupt and concurrency behavior. ● Commit changes to version control. Phase 4: Unit and Integration Testing Checklist examples: ● Test individual functions and modules. ● Test drivers against real hardware. ● Verify UART, SPI, I2C, ADC, PWM, DMA or other applicable interfaces. ● Verify error handling and boundary conditions. ● Test RTOS task interactions, if applicable. ● Verify communication failures and recovery. ● Run static analysis. ● Fix critical defects. ● Record test results and evidence. Phase 5: System Validation and Stress Testing Checklist examples: ● Verify complete system functionality. ● Test repeated startup and reset. ● Test power interruption and recovery. ● Test peripheral and communication failures. ● Measure CPU and memory usage. ● Perform a long-duration test. ● Verify timing requirements. ● Verify thermal and power behavior where relevant. ● Record known issues and limitations. Phase 6: Demo or Pilot Preparation Checklist examples: ● Freeze the demo firmware version. ● Verify the hardware configuration. ● Test the main use cases end-to-end. ● Verify startup and shutdown. ● Check logs and diagnostic messages. ● Verify recovery from expected failures. ● Prepare a known-good backup firmware image. ● Prepare setup and demonstration instructions. ● Record remaining issues. ● Complete the Product Release Gates checklist. Phase 7: Post-Demo Review Checklist examples: ● Record demo feedback. ● Record failures and unexpected behavior. ● Create follow-up tasks. ● Document improvements. ● Decide the next development milestone. These are default templates. Allow me to add, edit, delete, and reorder phases and checklist items. The phases must be configurable because not every embedded project requires every test. 7. Phase Workspace When I open a project, display its development phases in a clear vertical sidebar or timeline. When I select a phase, show: ● Phase description. ● Phase status. ● Phase completion percentage. ● To-do list. ● Pending tasks. ● Blocked tasks. ● Completed tasks. ● Due dates. ● Phase-specific notes. ● Linked technical references. ● Optional attachments. Allow me to add custom tasks at any time. Every task should contain: ● Title. ● Description. ● Status. ● Priority. ● Due date, optionally. ● Checklist items, optionally. ● Notes. ● Created date. ● Completion date. Task statuses: ● To Do. ● In Progress. ● Pending. ● Blocked. ● Done. I should be able to quickly add a task, check it off, edit it, delete it, and move it to another phase. Make the interface easy to use while I am actively developing firmware. 8. Phase Notes Sidebar Implement a right-side notes panel for each phase. When I click the notes icon, open a sidebar without navigating away from the current phase. Allow me to: ● Write technical notes. ● Record design decisions. ● Record bugs and debugging observations. ● Store commands and configuration details. ● Add useful reference links. ● Attach log files or screenshots where appropriate. ● Edit and search notes. ● Record the date of each note. Keep notes associated with the correct project and phase. Do not mix notes from different projects. Persist notes in the database so they remain available after restarting the application. 9. Product Release Gates — Most Important Feature Create a separate section called Product Release Gates. Its purpose is to help me verify whether an embedded product is ready before I give a demo, hand it to someone else, or move it to pilot deployment. Every project must have its own release-gate checklist. Provide three gate templates: Gate A: Before Demo ● Required functionality works. ● Main use cases tested end-to-end. ● Firmware build succeeds. ● Correct firmware version identified. ● Correct hardware and wiring verified. ● Required peripherals tested. ● Startup and reset behavior verified. ● Important error conditions tested. ● No unresolved demo-blocking defects. ● Logs and diagnostics checked. ● Recovery procedure available. ● Demo setup instructions prepared. ● Backup firmware or recovery image available where applicable. ● Known limitations documented. Gate B: Before Pilot Deployment ● All mandatory functional requirements verified. ● Required unit and integration tests passed. ● System validation completed. ● Relevant stress and long-duration tests completed. ● Power consumption verified against requirements. ● Memory usage and timing requirements verified. ● Communication-loss behavior tested. ● Power-loss recovery tested. ● Firmware update and recovery tested, if supported. ● Required security checks completed. ● Relevant environmental and EMC testing completed where required. ● No unresolved release-blocking defects. ● All exceptions and known limitations documented. ● Recovery and rollback instructions prepared. ● Pilot acceptance criteria documented. Gate C: Before Production Release ● Production firmware version frozen. ● Source revision and build configuration recorded. ● Firmware artifact checksum recorded. ● Required regression tests passed. ● Applicable compliance requirements satisfied. ● Production hardware revision confirmed. ● Manufacturing and programming procedures documented. ● Production test procedure validated. ● Device configuration and calibration procedures verified. ● Firmware recovery and servicing procedures documented. ● Release notes prepared. ● Known limitations and residual risks reviewed. ● Final release review completed. These checklists are defaults, not universal compliance requirements. Allow me to customize them per project and gate. 10. Release Gate Behavior Every checklist item must have a persistent checkbox and a clear state. When I open a gate, show: ● Gate name. ● Related project. ● Gate type. ● Total checklist items. ● Completed items. ● Incomplete items. ● Completion percentage. ● Failed or blocked items. ● Gate readiness status. ● Notes and evidence. Gate statuses: ● Not Started. ● In Progress. ● Blocked. ● Ready for Review. ● Passed. Do not mark a gate Passed merely because all boxes are checked. When all mandatory boxes are checked, change the status to Ready for Review. Then show a final confirmation action: Mark Gate as Passed. Before allowing this action: ● Confirm all mandatory checks are complete. ● Require me to confirm the firmware version or product configuration being reviewed. ● Display any unresolved blocking issues. ● Allow a final review note. After I confirm, record the gate result, timestamp, project, firmware version, and review note. For personal use, I can approve my own gate. Do not build complex multi-user approval workflows. If a gate has incomplete checks, clearly show which items are still pending. If a previously passed gate is affected by a relevant firmware or hardware change, warn me that the gate may need to be reviewed again. Do not silently erase its historical result. 11. Failure and Retest Tracking When a checklist item fails, allow me to: ● Mark it as Failed. ● Record what happened. ● Add debugging notes. ● Record the expected and actual behavior. ● Attach a log or screenshot. ● Create a corrective task. ● Mark the item as Fixed. ● Record the retest result. ● Mark it as Verified after successful retesting. Keep a simple history of the failure, fix, and retest. Do not let a failed item count as passed just because its corrective task is marked Done. Do not delete historical failure information when I retry the test. Keep this workflow simple enough for one engineer. 12. Personal Engineering Notes Create a separate Engineering Notes page. Allow me to capture notes across all projects, with filters by: ● Project. ● Development phase. ● Note category. ● Date. Categories: ● Technical Decision. ● Debugging. ● Hardware. ● Firmware. ● Testing. ● Bug. ● Reference. ● General. Allow searching note titles and contents. Each note should link back to its project and phase where applicable. 13. Progress Calculation Calculate project progress from completed development tasks and phase checklist items. Clearly define the calculation so progress does not jump unpredictably. Show: ● Completed tasks. ● Total active tasks. ● Phase progress. ● Overall project progress. ● Release-gate completion. ● Number of unresolved blockers. Keep development progress and release readiness separate. A project may be 100% complete in its task tracker but still not be ready for demo or pilot deployment. Do not use a single progress percentage as a substitute for gate verification. 14. Data Model Create a simple relational schema using Prisma and SQLite.
